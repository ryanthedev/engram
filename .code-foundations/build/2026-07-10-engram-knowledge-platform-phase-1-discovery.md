## Design Decisions

### Design: Knowledge message set (design-it-twice per aposd)

#### Approaches Considered
1. **A — Generic typed predicate/sort with oneof Value**: `Predicate{field, PredicateOp op, oneof value{google.protobuf.Value scalar | Range range}}`, `SortKey{field, SortOrder order}`; one `CollectionSpec{name, text_field, map<string,FieldSpec>, AccessPolicy}` message reused by Create/Update/Collections; docs carry `google.protobuf.Struct fields`.
2. **B — JSON-string escape hatch**: `string filters_json` / `string spec_json` (precedent: `Hit.fields_json`). Tiny proto, zero wire typing.
3. **C — Per-op filter fields**: `repeated TermFilter`, `repeated RangeFilter`, `repeated PrefixFilter` (+ per-field sort messages).

#### Comparison
| Criterion | A | B | C |
|-----------|---|---|---|
| Interface simplicity | 2 enums + 3 small messages | 1 string field | 3+ messages, grows per op |
| Information hiding | High — op set closed by enum, value typing on the wire | None — every consumer re-parses/validates JSON | Medium — ops leak into message structure |
| Caller ease of use | Typed, self-documenting | Caller hand-writes JSON, errors surface late | Caller picks the right repeated field per op |
| Extensibility (new op / new collection) | Add enum value; zero per-collection fields | "Anything goes" (no contract to freeze) | New message per op — surface grows |

#### Choice: A
Rationale: matches the plan's DECIDED `oneof{scalar Value | Range{gte,lte}}` representation; deep-minimal — the whole filter language is 2 enums + 2 messages, generic over any collection (DW-1.3). B sacrifices the frozen contract this phase exists to produce; C widens the surface per op. Sacrificed: A introduces the repo's first enums/oneof/map — acceptable, plan calls this out as the precedent-setter.

#### Depth Check
- Interface methods: 6 RPCs; new messages: 13 (incl. 2 empty-ish responses), 2 enums.
- Hidden details: index names/aliases (spec has NO `index` field — registry-internal), OpenSearch query DSL, harvested_at stamping.
- Common case complexity: simple — `KnowledgeSearch{collection, query, k}` with no filters/sort is a complete call.

### Design: Backend seam return type for KnowledgeSearch
- **A — reuse `mcp.Hit`** (`Source` = collection name) vs **B — new `KnowledgeHit` type**.
- Choice: **A**. Phase 6 must feed the budget-packer/spill which are typed on `mcp.Hit`; returning `[]Hit` from the seam eliminates the adapter type entirely (deep: one hit shape across both search paths). `Hit.Source` doc widened from "episodic|semantic" to include collection names. Proto side likewise reuses `Hit` in `KnowledgeSearchResponse`.

### Other decisions
- `KnowledgeIngestResponse{indexed}` only — no per-item error list: upsert-by-id is retry-idempotent, so partial-failure detail travels in the gRPC error (Phase 4 DW-4.4 contract: `BulkIndex` returns `(indexed, err)`); a full-batch retry is safe and cheap. Additive field later is wire-compatible if Phase 6 wants more.
- `KnowledgeDeleteRequest{collection, source, current_harvest_id}` — exactly the mark-and-sweep predicate (Phase 4 `DeleteByQuery` signature); response `{deleted}`.
- `CollectionInfo` embeds `CollectionSpec` + `count` + `newest_harvested_at`/`newest_doc_date` — the discovery tool teaches an LLM caller which fields are filterable/sortable (self-correcting usage), matching Phase 5 `Collections` staleness contract.
- mcp seam types flatten `AccessPolicy` into `CollectionSpec{Public, Roles}` (friendlier flat JSON for MCP tool args); proto keeps a nested `AccessPolicy` message (reusable, mirrors Phase 3's `knowledge.AccessPolicy`).
- mcp `Predicate{Field, Op, Value any}` mirrors Phase 5's produced `retrieval.Predicate{Field,Op,Value}`; a range travels as `{"gte":…,"lte":…}` map in `Value` — engramclient (Phase 6) maps it onto the proto oneof.
- engramclient stubs go in a new `internal/engramclient/knowledge.go` (Phase 6 replaces file contents, zero churn in client.go); they do NOT dial gRPC — they return a loud `"engramclient: <op>: not implemented (knowledge platform Phase 6)"` error, so a zero `Client` is safe to call in tests.
- `roles` added to `Provenance` as field 8 (`repeated string`), documented as populated from the verified token (Phase 2).
