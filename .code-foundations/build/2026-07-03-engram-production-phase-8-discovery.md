## Gaps
- **DW-1.3's non-inferiority check recomputes the "best single signal" every run** (BM25-only vs kNN-only, same run) rather than comparing against a frozen historical number. DW-8.2 explicitly wants the latter ("against the versioned baseline"). Design: add `gate.RegressionBaseline` (JSON, versioned, checked in) + `gate.CheckRegression(current, baseline, marginPP)`, and a `SeedFixtures`/measurement step that reproduces DW-1.3's exact seeding (fixture-keyed `FakeEmbedder`) but grades against the stored baseline instead of a same-run comparator. The DW-1.3 test itself is untouched (still proves fusion structurally beats either signal).
- **No hallucination-detection concept exists at all.** Building from zero: `eval.HaluJudge` (interface) + `eval.RuleHaluJudge` (deterministic token-overlap grounding check) + `eval.HTTPHaluJudge` (OpenAI-compatible, fail-closed on any error — mirrors `experience.HTTPGatekeeper`) + `eval.HaluGoldSet`/`HaluFixtures()` (a small checked-in-by-construction fixture corpus, Go literal like `experience.GoodFixtures()`) + `eval.RunHallucinationSuite`.
- **"Gates read-only against staging" vs. needing a corpus present to measure against.** Resolved by splitting **seed** (idempotent writes, run once when standing up an environment — same idempotent-converge idiom as `store.Apply`/`cmd/engram-deploy`) from **gate** (pure reads + local threshold/trend files only) into distinct, separately-invocable test entry points in the same package. The `gates` job in `deploy.yml` only ever runs the read-only one.
- **The bad-release drill must never fire against real staging.** `e2e`'s `Boot()` cannot distinguish "local compose stack" from "real staging" (both go through `ENGRAM_E2E_ADDR`) — a normally-registered `Scenario` or bare e2e test would auto-run during `make e2e-cloud` against staging on every deploy. Design: the drill is **opt-in via an explicit env var** (`ENGRAM_EVAL_DRILL=1`), skipped by default under any invocation (`make e2e`, `make e2e-cloud`, or a bare `go test -tags=e2e`), and only runs when a dedicated `make eval-drill` target sets it. This is a stronger guarantee than a "skip if external" heuristic (which cannot tell compose from staging) and needed a deliberate design decision, recorded here.
- **`cmd/engram-stub-llm`/`internal/ingest` are outside this phase's stated file scope** but the plan's own Scope-IN line names "intentionally degraded reconciler prompt" for the drill. Resolved without touching either: the drill ingests *directive text asserting facts unrelated to the known-good fixture corpus* through the **existing, unmodified** pipeline. `RuleExtractor`/the stub LLM faithfully "extract" whatever directive they're given (that is their whole design — syntax, not truth, validation), so this reproduces exactly what a degraded extraction prompt would produce (facts not grounded in source) with zero edits outside `internal/eval/**`, `e2e/**`, `docs/eval/**`, `Makefile`.
- File scope's `cmd/` omission: no new `cmd/` binary is created. The CLI-exposed, exit-code-gated surface is a `go test` binary (`internal/eval/gate`, tags `integration`), matching the codebase's existing convention (`make integration`, `make e2e-cloud`, `make drill` are all `go test` invocations, not bespoke CLIs) — this keeps everything inside `internal/eval/**` and `Makefile`, both explicitly in scope, and gives DW-8.1's "prove exit-code gating with a test/script" a literal, direct answer (a test binary's exit code *is* the gating mechanism).

## Code Standards
`docs/code-standards.md`: doc comments on every exported symbol; sentinel errors + `errors.Is`; `context.Context` first param on I/O; table-driven tests; every code-touching phase ships ≥1 dirty test; interfaces at the consumer (`HaluJudge` defined in `internal/eval`, not by its HTTP implementation); structured logs via `log/slog`. Applied throughout. The Rule/HTTP judge duality and fail-closed-on-error convention from `internal/experience` is followed exactly for `HaluJudge` (new precedent already established by a prior phase, not invented here).

## Test Infrastructure
- `go test ./...` (`make test`) — plain unit tests, no external deps. Gate package's pure logic (thresholds, quarantine/flaky detection, trend recording, boundary checks) lives here — fast, always run.
- `-tags=integration` (`make integration`) — live OpenSearch (`ENGRAM_OPENSEARCH_URL`, dev cluster confirmed reachable). New `internal/eval/gate` live tests (seed, measure+gate, bad-release drill) run here automatically via the existing `./internal/eval/...` glob in `make integration` / `ci.yml`.
- `-tags=e2e` (`make e2e` / `make e2e-cloud`) — full stack through MCP/CLI/gRPC. New `e2e/scenarios_eval.go` pack runs automatically; the opt-in drill test does not.
- `-tags=drill` — Phase 7's precedent for destructive/adversarial local-only exercises, never in `ci.yml`.

## Design Decisions

### 1. Where does "the gate" live: a new `cmd/` binary or a `go test` binary?
Chose **`go test` binary** (tags `integration`), package `internal/eval/gate`. Alternatives considered: a new `cmd/engram-gate` CLI (rejected — outside the stated file scope, and duplicates the exit-code-on-failure behavior `go test` already gives for free); folding gate checks into `cmd/engram-eval` (rejected — that binary is Phase-0's NullRetriever demo and touching it means touching `cmd/`, still out of scope, for no benefit over a test binary). A `go test` binary's PASS/FAIL *is* its exit code — `make eval-gate` failing is the CI block, with zero extra plumbing, and it fits the codebase's existing `make integration`/`make e2e-cloud`/`make drill` convention exactly.

### 2. Seed vs. gate as separate test entry points
`internal/eval/gate` splits `TestSeedEvalFixtures` (writes the regression gold corpus + hallucination fixture corpus, idempotent by fixed doc IDs) from `TestGate_Regression`/`TestGate_Hallucination`/`TestGate_Following` (pure reads + local threshold/trend files). `make eval-seed` runs the former, `make eval-gate` runs only the latter (`-run '^TestGate_'`). `deploy.yml`'s pipeline calls `eval-seed` once after `deploy-staging` (a normal write-bearing convergence step, same spirit as the deploy CLI's idempotent apply) and `eval-gate` after that, read-only, matching the constraint literally. `ci.yml`'s `integration` job runs the whole package unfiltered against its own throwaway container (seed+gate+drill all run there, which is fine — it's disposable).

### 3. Bad-release drill without touching `internal/ingest`/`cmd/engram-stub-llm`
Both are outside file scope. The RuleExtractor/stub-LLM take directives at face value (no truth-checking — confirmed by reading `rule.go`/`cmd/engram-stub-llm/main.go`). So "a degraded extractor" is reproduced from the *outside*: ingest directive text asserting something absent from the known-good fixture corpus (e.g. `fact: shadow-directorate | controls | the-nuclear-launch-codes`, sharing zero vocabulary with anything in `HaluFixtures()`'s corpus). The existing pipeline faithfully stores it as a fact; the hallucination judge correctly flags it as ungrounded. This is *more* faithful to HaluMem's actual measurement target (facts the corpus doesn't support, regardless of mechanism) than modifying the extractor would be, and needs no file outside the declared scope.

### 4. Bad-release drill must never touch real staging
`e2e.Boot()`'s external mode (`ENGRAM_E2E_ADDR`) is used identically by `make e2e` (local compose) and `make e2e-cloud` (staging) — there is no reliable runtime signal to tell them apart (a `localhost` string check is fragile and easy to defeat by a future staging-on-localhost dev setup). Chose an explicit opt-in env var (`ENGRAM_EVAL_DRILL=1`) that the drill test checks and skips-by-default without it, set only by the dedicated `make eval-drill` target. This is a deliberate, stronger-than-minimum safety choice given the blast radius of accidentally poisoning a shared staging environment on every deploy.

### 5. Judge algorithm for `RuleHaluJudge`
Deterministic token-overlap: lowercase, split on non-alphanumerics, drop tokens <3 chars (stopword proxy), require ≥50% of a statement's remaining tokens to appear in the corpus token set to call it "supported." Chosen over exact substring matching (too brittle — `RuleExtractor`'s `synthesizeStatement` renders `"subject predicate object"` verbatim from the directive, so substring matching would work for the direct case, but token-overlap is more robust to paraphrase and matches the same "proxy for an LLM judge, real judge is the `HTTPHaluJudge` swap-in" pattern already established for `RuleGatekeeper`/`RuleExtractor`). Threshold is a named constant with a boundary test at exactly 50%.

### 6. Regression baseline: re-record fresh rather than trust the Phase-1 doc's numbers
The Phase-1 discovery doc's recorded DW-1.3 numbers (holdout n=61: hybrid recall@10=1.0000, MRR=0.9508, nDCG@10=0.9632) are two phases old. Rather than hand-copy them into `eval/goldset/baseline.json`, I run the same measurement fresh against the current code + dev cluster as part of this build and record whatever it actually produces, with the git rev and timestamp — this **is** the "baseline re-record procedure" the runbook documents, executed once now to produce the initial baseline (never trust an unverified number as day-one truth).

### 7. Following-gate: consumes existing `experience.FollowingCorrelation`, no new math
`gate.CheckFollowingCorrelation(corr float64, band Band) GateResult` is a pure function over a scalar. The "per-release" correlation figure is computed by calling the already-existing, already-unit-tested `experience.FollowingCorrelation` over sample data (in this build: the deterministic fixture samples the Phase-5 harness already established as the reference derivation — a real production release would swap in live telemetry samples behind the identical scalar-in seam, with zero gate-code changes). Documented explicitly as a bootstrap: this phase's OUT list excludes "new eval research," and this is not new eval research — it's wiring an existing, proven metric into a threshold check.
