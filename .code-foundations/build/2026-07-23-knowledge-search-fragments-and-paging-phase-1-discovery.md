## Design Decisions

### Design: queryOpts (buildQuery options struct)
Plan pins the shape (`buildQuery(opts queryOpts) (body []byte, usePipeline bool)`); design latitude is field layout only.

**Approaches considered**
1. **A — flat unexported `queryOpts` struct**: the 8 existing inputs + 5 zero-value-safe Phase-2/3 seam fields (`offset`, `fragmentSize`, `numberOfFragments`, `highlightPreTag`, `highlightPostTag`), all inert this phase.
2. **B — nested sub-structs** (`queryOpts{ base…, highlight *highlightOpts, page *pageOpts }`): groups concerns but a nil-vs-zero pointer split breaks "zero-value-safe" (two ways to say off) and adds caller ceremony.
3. **C — functional options on buildQuery**: over-machinery for an unexported 2-call-site helper; hides which knobs exist.

| Criterion | A | B | C |
|-----------|---|---|---|
| Interface simplicity | one struct, zero value = today's memory query | two nil-able layers | N closures |
| Zero-value safety (plan Produces) | yes, by construction | no (nil vs &zero ambiguity) | yes but opaque |
| Caller ease (memory path) | `queryOpts{mode…, k…}` — omit the rest | must know sub-struct split | verbose |
| Phase 2/3 extension | add field + wire | same + pointer rules | add option func |

**Choice: A.** Zero-value opts must produce byte-identical memory queries — a flat struct where "unset" is the Go zero value makes that property structural. Parameter count collapses 8 → 1 (cc threshold: 8 was WARNING).
- Cohesion: `buildQuery` stays functionally cohesive (constructs one search body); the struct is a parameter object, not a class.
- Depth check: interface = 1 function, 1 options type; hidden: JSON shape, hybrid/pipeline coupling, filter nesting, `_source` excludes. Common case (memory) = 8 named fields, no new knowledge.

### Design: per-collection sizing fields + fallback
**Approaches considered**
1. **A — 4 flat fields on all three types + `FragmentSizing()` accessor on `knowledge.CollectionSpec` + exported defaults (240/3) in `internal/knowledge`**: the fallback rule lives once, at the domain type the retriever consumes (server-side `KnowledgeReader.Search(spec …)` already receives `knowledge.CollectionSpec`).
2. **B — nested `Highlight` message/sub-struct**: proto sub-message + 2 more Go types + deeper translation for 4 scalars — classitis for this size.
3. **C — global constants only (plan's fallback)**: only if translation proved invasive; it didn't (assumption 2 HOLDS).

**Choice: A.** `FragmentSizing() (size, count int)` hides "absent/zero/negative → default" from every consumer (Phase 2 just calls it); mcp/proto carry raw values (0 = unset survives the wire both ways — round-trip is lossless BECAUSE the fallback is applied at consumption, not translation). Tags (`HighlightPreTag`/`HighlightPostTag`) get NO fallback — both-empty = markers off is the plan's default, so the zero value is already correct.

### Wire/message decisions (plan-pinned, recorded)
- `KnowledgeHit { id=1; score=2; collection=3; fields_json=4; fragments=5 }`; `KnowledgeSearchRequest += offset=6, full_body=7`; `KnowledgeSearchResponse { repeated KnowledgeHit hits=1; int64 total=2 }`; `CollectionSpec += fragment_size=5, number_of_fragments=6, highlight_pre_tag=7, highlight_post_tag=8`.
- Phase-1 behavior bridge: server maps `retrieval.Hit.Source` (== collection name from `parseHits(decoded, spec.Name)`) → `KnowledgeHit.collection`; `fragments` empty, `total` 0, `offset`/`full_body` accepted-but-inert (Phases 2–3 wire them; nothing client-side sets them yet). `engramclient.KnowledgeSearch` keeps its `[]mcp.Hit` signature this phase (Phase 2 changes it) and maps `Collection` → `mcp.Hit.Source` so MCP/CLI behavior is byte-identical.
- Proto int types: `int32` on the wire (plan-pinned), plain `int` on both Go structs (house style for k/counts).
