# Discovery + Design: Phase 3 - Offset paging & vault export fix

## Files Found
- `internal/retrieval/opensearch.go` — `queryOpts` already carried zero-value-safe `offset`, `fragmentSize`, `numberOfFragments`, `highlightPreTag`, `highlightPostTag` fields (Phase 1/2); `buildQuery` did not yet read `offset` and had no `track_total_hits` concept.
- `internal/retrieval/knowledge.go` — `KnowledgeRetriever.Search(ctx, spec, query, filters, sortKeys, k int, fullBody bool) ([]Hit, error)` (Phase 2 signature); `Collections`/`collectionMeta` already used `track_total_hits`+`totalHits()` for the staleness aggregation, so the `totalHits` helper existed and was directly reusable.
- `internal/server/knowledge.go` — `KnowledgeReader` interface and `KnowledgeSearch` handler; proto already exposed `req.offset`/`req.full_body`/`resp.total` (Phase 1), but the handler ignored offset and always left `total` at its zero value (comment said "Phase 3").
- `internal/engramclient/knowledge.go` — `Client.KnowledgeSearch(ctx, collection, query, filters, sortKeys, k int, fullBody bool) ([]mcp.KnowledgeHit, error)`.
- `internal/mcp/mcp.go` — `Backend.KnowledgeSearch` interface matching the engramclient signature (Client implements Backend); `internal/mcp/tools.go` `callKnowledgeSearch` had no `offset` arg.
- `internal/cli/vaultknowledge.go` `fetchKnowledgeDocs` — one unpaged `KnowledgeSearch(..., retrieval.MaxK, true)` call per collection, with a `len(hits) == MaxK` truncation warning and a stale "the RPC has no offset/cursor" comment (lines ~63-91 in the pre-Phase-3 file).
- `api/proto/engram.proto` — `KnowledgeSearchRequest.offset`/`full_body` and `KnowledgeSearchResponse.total` already existed (Phase 1); no proto change needed this phase.
- No existing `max_result_window`/`MaxResultWindow` constant anywhere in the repo (grepped `max_result_window|MaxResultWindow|track_total_hits`) — confirms the plan's Assumption-table fallback applies: add an explicit constant.

## Current State
Phases 1–2 built the wire shapes and fragment extraction; `offset`/`total` were plumbed onto the proto as inert fields. `vaultknowledge.go` still called `KnowledgeSearch` with `fullBody=true` as a stopgap, fetched exactly one page of `retrieval.MaxK` (100) docs per collection, and warned (not failed) when a collection returned exactly 100 hits, on the theory that more might exist but the RPC had no way to reach them.

## Gaps
- `buildQuery` needed to emit `"from"` (offset>0) and `"track_total_hits"` (gated by a new flag, not by offset, since a `fullBody=true` page-1 call also needs an exact total for `fetchKnowledgeDocs`' loop-termination condition).
- No `max_result_window` bound existed anywhere — a caller requesting `offset+k` beyond OpenSearch's default 10000-result window would hit a raw `search_phase_execution_exception` (an ugly 500), not a self-correcting error.
- `KnowledgeRetriever.Search`, `KnowledgeReader.Search`, `engramclient.Client.KnowledgeSearch`, and `mcp.Backend.KnowledgeSearch` all needed a new `offset` parameter and a `total int64` return value, in that consistent parameter position (mirroring the plan's explicit Go contract for `engramclient.KnowledgeSearch`).
- Every existing call site of any of those four signatures (production and test) needed updating — a wide but mechanical blast radius: `internal/mcp/tools.go`, `internal/mcp/mcp_test.go`, `internal/mcp/knowledge_tools_test.go`, `internal/server/knowledge_test.go` (fake), `internal/server/knowledge_integration_test.go`, `internal/server/knowledge_fragments_integration_test.go`, `internal/engramclient/knowledge_test.go`, `internal/cli/vaultknowledge.go`, `internal/cli/export.go`, `internal/cli/export_test.go` (the `exportStub.KnowledgeSearch` fake previously ignored offset/k entirely, returning the full canned slice every call — that would have made the new paging loop in `fetchKnowledgeDocs` fetch the same full page forever without ever converging, so the fake itself needed to become offset/k-aware).
- The plan's Test Plan calls the old truncation-warning test the thing DW-3.3 replaces; the fake's un-paged behavior meant the old `TestKnowledgeCollectionTruncationWarning` test needed to become a real multi-page drain test, which required teaching the fake real `from`/`size` slicing semantics.

## Code Standards
`docs/code-standards.md` conventions applied: `internal/engramclient` stays the sole gRPC transport boundary (no new status-code classification needed here — the clamp error surfaces through the existing uniform `codes.Internal` wrap, matching how `buildFilterClauses`'s defense-in-depth errors already surface); sentinel/plain errors returned unwrapped with `fmt.Errorf`/`%w` where wrapping an underlying error, self-correcting messages naming the offending values and the valid range/cap; stdlib `testing` with in-process gRPC-stub/httptest-server fakes; doc comments carrying the "why", not just the "what".

## Design Decisions

**`trackTotalHits` as its own `queryOpts` flag, not derived from `offset>0`.** `fetchKnowledgeDocs` needs an exact total on its FIRST call (offset=0) to decide whether to page at all, and it always passes `fullBody=true`. So `track_total_hits` must be requested unconditionally by `KnowledgeRetriever.Search` regardless of `fullBody` or `offset`, while staying off (zero-value) for every memory-tier caller of the shared `buildQuery`. A dedicated boolean, set unconditionally in `Search`, keeps the golden-body byte-identity for memory queries intact (DW-1.3) while giving the knowledge path an always-exact total.

**`MaxResultWindow` and the clamp live in `internal/retrieval` (not the server barricade).** The plan's file scope for the clamp names `opensearch.go`/`knowledge.go`; the Assumption table's fallback ("add an explicit `MaxResultWindow` const, default 10000") confirmed no existing bound to reuse. Placing the clamp inside `KnowledgeRetriever.Search` — before any HTTP call — means it fires for every caller of the retriever (defense-in-depth, matching the existing `buildFilterClauses`/`buildSortClauses` precedent of validating inside the retriever even though the server barricade also validates upstream inputs). The resulting error surfaces through the server's existing uniform `status.Errorf(codes.Internal, "searching collection %q: %v", ...)` wrap — consistent with how the retriever's other defense-in-depth errors (e.g. an out-of-band unfilterable-field error) already surface, so no new gRPC-code branch was introduced.

**`clampOffset` silently normalizes negative input to 0, mirroring `clampK`.** A negative offset can never mean anything legitimate ("skip -5 hits"); rather than a hard validation error deep in the retriever, it clamps to the existing "0 = first page" sentinel, exactly like `clampK` silently normalizes out-of-range `k`. The MCP tool boundary (`callKnowledgeSearch`) additionally rejects a negative `offset` outright as a tool error — external input arriving directly from an LLM caller gets a loud correction there, while the retriever itself (also reachable from the CLI/other Go callers, not just the validated MCP path) stays robust rather than panicking or erroring on a value that has an obvious safe interpretation.

**`offset` inserted between `k` and `fullBody` in every threaded signature**, exactly matching the plan's explicit Go contract for `engramclient.KnowledgeSearch(ctx, collection, query, filters, sort, k, offset int, fullBody bool) (hits, total, err)`. The same parameter order was mirrored through `KnowledgeRetriever.Search`, `KnowledgeReader.Search`, and `mcp.Backend.KnowledgeSearch` for consistency across the four seams the plan says extend Phase 2's signature.

**`offset`/`total` also threaded through the MCP tool boundary (`callKnowledgeSearch` args + `searchResult.Total`), beyond the plan's literal file-scope wording.** The plan's Produces line states "`knowledge_search` accepts `offset` and returns exact `total`" without qualifying gRPC-only — and `knowledge_search` is the literal name of the MCP tool a caller invokes, matching Phase 2's own precedent of surfacing `full_body` as a tool argument once it went live at the wire level. `mcp.Backend`'s interface signature already had to gain `offset`/`total` for `engramclient.Client` to keep satisfying it (mandatory, not optional), so exposing the same values at the JSON-RPC tool boundary completes the threading the plan explicitly calls out for that interface method, rather than leaving it half-wired. `searchResult[H].Total` is a new `omitempty` field on the struct shared with `memory_search`; `memory_search` never sets it, so its zero value stays absent from that tool's JSON (verified: no memory_search test assertions changed or broke).

**`fetchKnowledgeDocs` drops its `warnings []string` return value entirely** rather than keeping the plumbing for a hypothetically-future warning: the only warning it ever produced was the one Phase 3 explicitly deletes, and no other warning source exists in this function today. `export.go`'s call site simplified from a 3-return to a 2-return call accordingly.

**Test-fake fidelity: `exportStub.KnowledgeSearch` (internal/cli/export_test.go) was upgraded to real `from`/`size` slicing over its canned `docs` map**, rather than continuing to return the whole slice on every call. Once `fetchKnowledgeDocs` loops on `offset`, a fake that ignores `offset` would make every page identical and the loop would never converge (`offset` would grow past `total` eventually since `offset += len(hits)` and `len(hits)` would stay constant and nonzero only if the fake always returns nonempty — actually with the OLD stub it would loop until `offset >= total`, which does terminate, but would silently produce a WRONG (duplicated) result rather than a true multi-page drain, defeating the point of the test). Teaching the stub real offset semantics makes the CLI-level test an honest proof of drain-to-completion.
